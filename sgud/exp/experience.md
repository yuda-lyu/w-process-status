# 經驗

本檔記執行時之累積經驗,留給後續嘗試、執行、判斷.

## 外部執行檔改造(bin-procstat,2026-10-28)

- **UMD 主檔不可改為具名匯出**:`main` 為 `dist/w-process-status.umd.js`(rollup UMD,`module.exports = 函數`).為了「匯出 `ensureBins()`」若在 `WProcessStatus.mjs` 加具名 `export { ensureBins }`,rollup 會改輸出 `exports.default`/`exports.ensureBins`,`require('w-process-status')` 之既有用法即壞.作法:`src/ensureBins.mjs` 預設匯出,並於函數上掛 `WProcessStatus.ensureBins`.
- **UMD 內之 `import.meta.url`**:rollup 3.29.5 於 UMD 輸出換為 `require('url').pathToFileURL(__filename).href`,故 `src/ensureBins.mjs` 以 `import.meta.url` 推套件根在 `dist/` 載入時亦正確(`dist/` 與 `src/` 同為套件根之下一層).驗證法:於 `./tmp` 另建 `dist`(不動 repo 之 `dist/`),組一個只含 `dist/*.umd.js` 與 `bin/manifest.json` 之假套件,離線無快取時看錯誤訊息之應放路徑是否為 `<假套件>/bin-cache/…`,再以本地鏡像實跑 `WProcessStatus`.另須把 `url`、`crypto`、`stream`、`stream/promises` 列入 `gDistRollup.mjs` 之 external 與 globals,否則建置有「guessing」警告.
- **測試之外網與落點**:`WProcessStatus.test.mjs` 原直接用 `src/processStatus.exe`,改造後取得會連 GitHub,須於 `before` 設 `W_BIN_CACHE`、`W_BIN_MIRROR`(本地資料夾,結構 `<鏡像>/w-process-status/<sha256>/processStatus.exe`)、`W_BIN_OFFLINE=1` 並於 `after` 還原環境與刪夾具.
- **`npm pack --dry-run` 與平行測試**:mocha `--parallel` 時他檔於 `test/_tmp/` 放之 exe 副本會被打包而使 T1 偶發失敗,故 `.npmignore` 須有 `test/_tmp`,且 T1 測試先放探針檔 `test/_tmp/binManifest/probe.exe` 確保此規則真有被檢查.
- **npm 包檢查之口徑(2026-11-02)**:npm 包＝git 版控之內容,`sgud/`、`docs/`、`test/`、`toolg/` 皆隨包,測試不得斷言其「不在」包內(舊斷言曾要求 `sgud/` 不在包內,`.npmignore` 移除 `sgud` 列後即紅);「不得入包」只列執行檔/壓縮檔等(dspec 自有套件之npm發布範圍 原則 2).驗證測試真有擋力之變異:放假 `src/*.exe`、`dist/*.dll`、`CLAUDE_*.md`(並暫時拿掉 `.npmignore` 之 `CLAUDE*.md`)、`.npmignore` 加 `sgud`／`src/ensureBins.mjs`／`!/bin/processStatus.exe`,皆紅;`.npmignore` 一旦存在 npm 即不讀 `.gitignore`,故首段須完整抄 `.gitignore`.
- **npm 12 `npm i` 副作用**:`npm i wsemi@1.9.27` 會把 `package-lock.json` 之 `resolved` 欄全部移除(Verdaccio 環境)、補 `package.json` 檔尾換行、並把鎖檔 root 之 version 同步為 package.json 之 1.0.27;非本輪所改,屬 npm 行為.移除 `postinstall` 後 root 之 `hasInstallScript` 須一併由鎖檔移除.
- **等測試鎖**:`quiet-run --lock` 於他套件持鎖時會等數分鐘(本輪第一次等 4 分鐘);把等待中之背景指令與「不影響該測試之文件撰寫」並行,但不可在等鎖期間改動會影響該次測試之 src.

## 清單補 exe、ppid、parentAlive 與 opt.timeout、state(Gitea #55,pr55,2026-11-03)

- **`Process.parent()` 的三個陷阱**(讀 psutil 7.2.2 `__init__.py` 的 `parent()` 與 `_pswindows.py` 並實測):①`parent()` 開頭 `if self.pid == lowest_pid: return None`,Windows 最小 pid 為 0,故 `System Idle Process` 的 `parent() is not None` 為 `False`——草案(`parentAlive = proc.parent() is not None`)會把它判為孤兒;②System(pid 4)的 ppid 為 0,而 pid 0、4 的 `create_time()` 皆為 0.0,`parent.create_time() <= proc_ctime` 成立,故 `parent()` 回 Idle 而得 `True`,是杜撰的父子關係,本案兩者皆 `null`;③`<=` 使「建立時間相同」視為存活,邊界以 mock 驗證(相同、差 ±1 微秒).草案的 `except Exception: None` 對 AccessDenied 確實得 `null` 而非 `false`(mock 驗證;真實系統 264 個行程未出現 `parent()` 拋例外,只有 `exe()` 對 Idle 拋 AccessDenied).
- **pid 重用可實測**:Windows 的 pid 約 2600～3100 次短命行程啟動後會回到已結束行程的 pid(`tmp` 探測腳本:殺中介行程、以 `cmd /c set /p x=` 反覆起行程至 pid 相符,當下新行程存活),此時 `psutil.pid_exists(ppid)` 為 `True`(使用端若只用 `process.kill(ppid, 0)` 會判存活)而 `parentAlive` 為 `false`(新行程建立時間晚於孫行程).不放入 JS 測試(耗時且不確定),證據在報告.父行程已被 TerminateProcess 但他處仍握有其 handle 時,psutil 亦判不存在(`NoSuchProcess`),`parentAlive` 為 `false`.
- **`parent()` 太慢,改自行實作等價判定**:`Process.ppid()` 在 Windows 每次呼叫 `ppid_map()`(全系統行程快照約 5 ms),`parent()` 每行程合計約 9 ms,94 個 `svchost.exe` 使查詢多約 0.77 秒;改為一次 `psutil._psplatform.ppid_map()`、同一 ppid 之父行程建立時間只查一次,多 67～179 ms(兩輪;剩餘部分為服務行程之 `create_time()` 走慢路徑,每個約 1.8 ms).自行實作須與 `parent()` 全行程逐一比對(兩輪各 264、262 個 0 筆不一致).
- **Python 3.14 的 `codecs.open` 棄用警告進了 `state`**:當時工具鏈(3.14.3)建出之執行檔每次執行於 stderr 印 `DeprecationWarning: codecs.open() is deprecated`,`execProcess` 合併 stdout 與 stderr,故失敗原因前面多一行雜訊並占掉 200 字元上限;1.0.33 官方舊檔(內嵌 `python311.dll`)無此警告.改 `open(..., newline='')`(`codecs.open` 為二進位模式、不轉換換行).pr55b 起執行檔改 3.13 建置,該警告不再出現,`open` 仍保留(3.13、3.14 皆可用).
- **逾時強制結束會留 `_MEI*`**:PyInstaller 單檔執行檔啟動時解壓到 `%TEMP%\_MEI*`,被 `taskkill /T /F` 結束則不會清除,實測每次逾時留一個(3.14 建置 13～17 MB;pr55b 以 3.13 建置重測為 14.1～14.8 MB,限制不變).測試把 `TEMP`/`TMP` 導到 `test/_tmp/WProcessStatus/tmp`(`os.tmpdir()` 與子行程皆跟著走),由 `after` 刪夾具即清掉;對使用端只能文件註明.
- **讓真執行檔自己失敗以測 `state`**:執行檔內部失敗時離開碼仍為 0,原因只印 stdout.測試攔截 `fs.writeFileSync`,對檔名結尾 `_fpIn.json` 的寫入改成損壞內容(`{`)或不寫,執行檔即回報 `error: ...`(json 錯誤或 `[Errno 2]`);長度上限用「`TEMP` 補長到 150 字元」讓路徑類錯誤超過 200 字元,斷言只依 `TEMP` 長度,不能假設套件所在路徑長短(變異副本放在更深處時曾因此誤紅).
- **建置**:`./tmp/pr55/venv` 裝 `psutil==7.2.2`(2026-01-28 發布)、`pyinstaller==6.22.3`(2026-09-12);`python -m PyInstaller --noconfirm --distpath <tmp> --workpath <tmp> srcPython/processStatus.spec` 約 7～10 秒.同一原始碼重建所得雜湊不同(PyInstaller 非可重現建置),故先定稿原始碼再建置、建置後才寫清單.`build.bat` 之 `-F` 會覆寫 spec,且第二行 `build.spec` 檔名不符,不要直接跑.PyInstaller 分析不會寫 `srcPython/__pycache__`,但以 `importlib` 載入 `srcPython/processStatus.py` 做探測會(須 `-B`/`sys.dont_write_bytecode`).
- **清單釘選提交與代理不得提交之衝突**:換執行檔後清單 `sha256`/`size` 可由代理更新,`commit` 欄須為含新檔之提交,代理做不到;`unit-binManifest` 的「pinned commit」一案必紅直到主控兩步提交(先提交執行檔,再 `genBinManifest --commit`).
- **Git Bash 的坑**:`tasklist /FI ...` 被轉換成 `C:/Program Files/Git/FI`(路徑轉換),須 `MSYS_NO_PATHCONV=1` 或用 `execFile`;GNU `tar -xf C:\...` 把 `C:` 當遠端主機,用相對路徑 + `-C`.

## 執行檔改以 Python 3.13 重建(pr55b,2026-11-03)

- **為何 3.13**:業主部署含 Windows Server 2016.docs.python.org 3.13 的 Windows 頁載明「Python 3.13 supports Windows 8.1 and newer」,3.14 載明「Python 3.14 supports Windows 10 and newer」(並稱 Windows Server 2019 是唯一不支援 MSIX 的受支援 Windows),Server 2016 在 3.14 下不明確;使用者定「用 3.13」,只重建、不做雙版本或自動降級.3.13 頁另有一句「Microsoft Store 版需 Windows 10 以上」,是指商店版,不是 CPython 本身.3.13 安全修補維護至 2029-10(PEP 719),屆時再評估.
- **取得無安裝之 Python 3.13**:python.org 的 Windows 安裝檔會寫登錄檔,不用;官方 NuGet 套件 `python`(發布者 Python Software Foundation)解壓即得完整 `tools/`(含 `Lib`、`DLLs`,可 `-m venv` 與 `ensurepip`):`https://api.nuget.org/v3-flatcontainer/python/3.13.17/python.3.13.17.nupkg`(14.8 MB).3.13.17(2026-10-21)為 3.13 最後一個附 Windows 建置之版本(PEP 719:「exceptionally with binary installers」,其後僅原始碼).
- **核對來源**:①NuGet 目錄(`https://api.nuget.org/v3/catalog0/data/<時間>/python.3.13.17.json`)之 `packageHash`(SHA-512,base64)＝以 `openssl dgst -sha512 -binary | openssl base64 -A` 算得者;②套件內 `python.exe`、`pythonw.exe`、`python313.dll`、`python3.dll`、`vcruntime140*.dll` 與 python.org 之 `python-3.13.17-embed-amd64.zip` 內同名檔 SHA-256 全同;③該 zip 之 `.asc` 以 GPG 驗為 Steve Dower(Python Release Signing)之 Good signature(金鑰 `7ED1 0B65 31D7 C8E1 BC29 6021 FC62 4643 4870 34E5`,keys.openpgp.org 會因缺使用者 ID 略過匯入,改取 `keyserver.ubuntu.com` 的 `pks/lookup?op=get&search=0x<keyid>`;金鑰指紋未另與 python.org 頁面交叉,屬信任鏈缺口).NuGet 包內的 `.signature.p7s`(作者簽章)未驗(無 dotnet/nuget).
- **解壓**:Git for Windows 的 GNU tar 不認 zip／nupkg,用 `C:\Windows\System32\tar.exe`(bsdtar)並以相對路徑 + `-C`;nupkg 內有 `.signature.p7s` 隱藏檔,`ls` 要加 `-a` 才見.
- **確認執行檔內為 3.13 的三個證據**:①建置 log 的 `Python: 3.13.17` 與 `Using Python shared library: …python313.dll`;②`pyi-archive_viewer -l -r processStatus.exe` 列出之打包內容只有 `python313.dll`、`python3.dll`;③實跑時(TEMP 導向 `./tmp`)輪詢 `_MEI*/python313.dll` 出現即樹狀終止,其 SHA-256＝官方包之 `python313.dll`.`tasklist /M` 在行程 0.3 秒內抓不到載入模組(`null`),不能當證據.
- **3.13 與 3.14 的差別**:同一原始碼、同一 PyInstaller／psutil 版本,3.13 建出之執行檔 7,824,932 位元組(3.14 為 8,681,283);3.13.17 的 `codecs.open` 無棄用警告(`-W error::DeprecationWarning` 實測;3.14.3 同法會拋 `DeprecationWarning: codecs.open() is deprecated`);逾時殘留 `_MEI*` 兩版皆實測存在(3.14 為 13～17 MB,3.13 為 14.1～14.8 MB).
- **量測受本機負載影響**:同機他套件測試並行時,單次執行 1.1～2.5 秒(空閒時約 0.77 秒),新舊檔差在雜訊內(±53 ms 以內);要比較只能取多次中位數並交錯執行,或在空閒時量.
- **PyInstaller 輸出非可重現**:同一原始碼、同一環境重建所得雜湊不同,故清單 `sha256` 必須取自最終要放進 `bin/` 的那一份;本輪建置一次、複製兩份、`cmp` 確認 `bin/`＝`src/`.
